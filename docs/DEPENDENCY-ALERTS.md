# Dependency alerts

Every alert gets read and the reading gets written down here, **including "no
exposure"** — that entry is what records that somebody looked.

A standing red count with nobody looking is worse than no scanner at all: it
trains everyone to scroll past the one that matters. If this file is empty and
the alert count is not zero, the process has stopped working.

## How to triage one

1. Is the vulnerable code path reachable from this package? Most alerts on a
   build-time dependency are not.
2. Is there a fix that does not move a major version?
3. **Never take `npm audit`'s advice unread.** On the sibling project its
   proposed remedy for one alert was to move a runtime dependency back three
   major versions.
4. Record the decision below with the date, whatever it was.

The general rule this repository now owns: **a floor is a claim about the WORST version you have said you will accept, and `npm audit` never checks it** — it audits what resolved. Audit the floors too, and both halves of that are now automatic. The half that needs no network is a gate: `test/floors.test.ts` over `scripts/dependency-floors.mjs` holds every declared floor against the version the lockfile installs, so **the floor is always a version the whole gate has already run**. The advisory half needs the registry and a database that changes daily, so it is a weekly job rather than a required check — `.github/workflows/floor-audit.yml` runs `scripts/audit-floors.mjs`, which pins every range to its own lower bound and audits that tree, and keeps ONE issue for the answer — filing it, commenting and reopening while a floor is bad, and commenting and closing it once every floor is clean again, so a fixed range does not leave a report standing that still reads as live. It runs a control arm against `@xmldom/xmldom@0.9.8` first and refuses to report on the real floors at all if that comes back clean, because a sweep whose failure mode is a good-looking result has to measure its own baseline. |
